How a link becomes an answer

A technical walkthrough of what happens between pasting an Amazon product link and seeing whether Flipkart, Croma or Myntra sell the exact same thing.

POST /api/compare  { "url": "https://www.amazon.in/dp/B0GVYGLNH7" }
Founding Backend Engineer assignmentNovember 2026
Overview

One link in, a verdict per store out

You paste an Amazon.in product link. About four to fifteen seconds later you see, for each relevant store, one of three answers: the same product is in stock, it is out of stock, or it is not listed. Exactly three, as the brief asks. A store that can't be reached is shown as not listed with a visible note saying it couldn't be checked, so a failure is never passed off as an absence.

1  Architecture

Two services, four stores

The system is deliberately small: a Next.js frontend that renders the page and proxies API calls, and a FastAPI backend that does all of the work. Both ship as containers and start with docker compose up --build.

2  The request, step by step

Tracing one real lookup

Everything below is from an actual run. The link is a OnePlus Nord CE6 Lite, 8 GB RAM, 128 GB storage, in Vivid Mint. The full round trip took 3.9 seconds.

1

The browser sends the link

The page posts {"url": "...", "refresh": false} to /api/compare on its own origin. Next.js rewrites that path to the backend, so the browser never needs to know where the backend lives and there are no cross-origin requests in production.

2

The backend finds the product ID

Amazon links come in many shapes: /dp/, /gp/product/, /gp/aw/d/ from the mobile app, long tracking URLs, and amzn.in short links. A regex extracts the 10-character ASIN; short links are followed to their redirect target first. The ASIN is the cache key: a repeat lookup within 15 minutes returns instantly unless the user presses "Check again".

3

The Amazon page becomes facts

The canonical page amazon.in/dp/ASIN is fetched and turned into a structured listing (section 3 explains how):

{ "brand": "OnePlus",  "category": "smartphone",  "colour": "Vivid Mint",
  "ram_gb": 8,  "storage_gb": 128,  "price": 30999,  "available": true,
  "title": "OnePlus Nord CE6 Lite | 8GB+128GB | Vivid Mint | Segment's Fastest Dimensity…" }
4

Each store is searched at the same time

The category decides the stores (Flipkart and Croma for a phone). Each gets a list of queries, tried in order until one produces a match: OnePlus nord ce6 lite 8GB RAM 128GB, then … Vivid Mint 128GB, then OnePlus nord ce6 lite.

5

Every result is judged

Flipkart returned 24 listings and Croma 6. Each one is turned into facts and compared with Amazon's: hard rules first (anything that breaks one is dropped with a reason, figure 4 shows Croma's six), then a learned score for the rest.

6

A winner is picked and its stock confirmed

Among listings that passed, the same colour wins. Stock is read from the store's own signal, opening the product page when the search result doesn't say.

7

The answer is rendered

{ "platform": "croma", "status": "in_stock", "price": 30999, "confidence": 1.0,
  "title": "OnePlus Nord CE6 Lite 5G (8GB RAM, 128GB, Vivid Mint)",
  "query": "OnePlus nord ce6 lite 8GB RAM 128GB", "candidates_checked": 6,
  "reasons": ["brand OnePlus matches", "model ce6 lite matches", "storage 128GB matches",
              "RAM 8GB matches", "same colour (Vivid Mint)"] }

The page shows Amazon as the reference row and one row per store, with the price difference against Amazon (Flipkart: ₹28,099, ₹2,900 less). The page stays as simple as the brief: one result per store, no extra detail.

3  Reading the Amazon page

From a marketing title to comparable facts

Amazon titles are written to sell, not to be parsed: "OnePlus Nord CE6 Lite | 8GB+128GB | Vivid Mint | Segment's Fastest Dimensity 7400 Apex Processor | 7000mAh Battery…". So the backend prefers structured data. Amazon's spec tables come in at least four layouts (product overview, tech specs, detail bullets, fashion "product facts"); all are merged into one key-value map with keys like brand, model name, colour and item model number. The title fills any gaps.

Category detection, in order

  1. Breadcrumbs mention smartphones, televisions, t-shirts/polos/jerseys, or shoes/sneakers.
  2. Spec-table evidence: a phone operating system (iOS, Android, One UI…) plus storage or SIM details. This rescued a real page titled just "iPhone Duo (512 GB) - Night Sky" with no breadcrumbs.
  3. Title words: "smartphone", "mobile phone", "iPhone", "TV" with a size, "polo", "jersey", "sneakers"…

Accessory words ("case", "cover", "compatible with"…) only guard the title check: a replacement iPhone screen is rejected, but a phone whose title boasts "45W Fast Charger" still counts. Other categories get a clear 422.

Why not just compare titles? "Galaxy S24" and "Galaxy S24 Ultra" share 90% of their characters, and "8GB RAM" vs "6GB RAM" differ by one digit. String similarity calls these near-identical; comparing extracted facts does not.

4  Searching the stores

One adapter per store, one interface

Each store is reached the way its own website gets its data, with a real Chrome TLS fingerprint (curl_cffi) so requests look like a normal browser visit. Every adapter turns results into the same Listing shape, so the matcher never knows which store it is looking at.

Query building, by category

Failure handling

Retries with a fresh session. HTTP 401/403/429/5xx and network errors trigger one retry (two for Amazon) with a reset cookie session and back-off.

Errors are never silent. If every query to a store fails, the whole store check is retried once with a fresh session. If it still fails, the row shows Not listed with the note "didn't respond, try again".

Isolation. Each store runs in its own guarded thread; an exception in one is contained to that store's row and the others still answer.

Captchas. If Amazon serves one, the session is reset and retried once, then the user is told plainly to try again shortly.

5  The matching engine

Identifiers, hard rules, then a learned score

The matcher (backend/app/match2) is the second version. The first was a chain of hand-written checks that grew with every failing link; the rewrite replaces it with four general steps, described by one table per category instead of branches in code. A wrong match is worse than a miss, so anything uncertain becomes "not listed".

1. Facts

Every listing, Amazon's included, becomes the same record: brand, the model's own name words, version words (anything with a digit, plus words such as Pro, Plus, Ultra, Lite, Mid, Slip-ins), manufacturer codes, and the category's attributes (RAM, storage and network; screen size; wearer, pack size, colour and the brand's shade name; garment, sleeve, neck, fit, pattern). Store conventions are handled here, once: "Pro+" means Pro Plus, Flipkart's escaped slashes, Croma writing "5G" on every 5G phone.

2. Identifiers first

If both sides carry a manufacturer code, the code decides. A TV model code (exact, a one-letter regional variant, or Croma's series code; a revision suffix like K-55S25B vs K-55S25BM2 is a different set) or a shoe/garment style code (177288-MVE; IU1397 is the Manchester United home kit even when sold as a plain T-shirt). A conflicting code rejects outright.

3. Hard rules, from one table per category

  • Phones: equal storage, equal RAM when both state it (Apple never does), same network (the REDMI A7 Pro 5G is not the 4G A7 Pro), and identical version words (Galaxy S24 vs S24 Ultra).
  • TVs: screen within ±1 inch, which absorbs 138 cm vs 139.7 cm rounding.
  • Shoes and clothes: same brand, compatible wearer, same pack size, compatible colour; when both sides give a brand shade name ("WOLF GREY", "MAUVE"/"MVE") it must agree. No version word may conflict (574 vs 574 Legacy; low top is the default).

4. A learned score for what's left

Name evidence is weighted by rarity: how many distinct products in the store data use a word. A shared rare word ("Malden", "teamLIGA", "025") is strong evidence; a common one ("Galaxy", "Running") barely counts, and a rare word on only one side counts against. These features feed a small logistic regression per category, fitted on 12,396 hand-labelled listing pairs in plain Python (no libraries, no model files beyond a JSON of weights). Each category's acceptance threshold is chosen by cross-validation to favour precision. The score only ranks and accepts; it is never shown as a "maybe".

Rebuild: scripts/build_background.py (word rarity, from tuning-set pools only) and scripts/train_v2.py (weights and thresholds). SCRUGE_MATCHER=v1 switches back to the old matcher for comparison.

6  Choosing the winner and the stock verdict

Same colour first, then the store's own word on stock

Phones are listed once per colour (and sometimes once per seller), so several listings often pass every check. The assignment only requires RAM and storage to match, but a different colour is not what the user asked for, so the winner is chosen by an ordered key:

# service.py (simplified)
def rank(match):
    score, listing, _ = match
    tier = colour_tier(source, listing)   # exact name, then same shade (off-white beats white), then base colour
    return (tier, round(score, 2), listing.available is not False, listing.available is True)

best = max(matches, key=rank)

If the exact colour is sold out

The result is Out of stock, because that is the true answer for that product, with a note: "This colour is sold out, but the same model is available in Marble Gray, Onyx Black." Before concluding that, up to three equally ranked listings are opened, since a store can list the same variant twice.

If the colour isn't listed at all

The closest variant is shown with its score reduced by 10% and a visible warning: "Same model, RAM and storage, but in Hyper Black: the Vivid Mint version isn't listed here."

The three outcomes

StatusWhenShown as
In stockA listing was accepted and the store says it can be bought.Solid green mark, "Buy" button, price and difference from Amazon.
Out of stockA listing was accepted but the store says it can't be bought right now.Half-filled amber mark, "View" button.

Right model, wrong colour. A Myntra product page lists the product's other colourways. When a listing is the right model in the wrong colour, the app opens the colourway whose colour fits Amazon's and judges it like any listing; this is how the off-white Court Vision Alta is found. Flipkart doesn't expose colourways to a plain request, so there they only appear as separate search results.

Every verdict is explainable. Each result carries a reasons list (in the API and scripts/try_link.py): the query used and each check that passed, or, for "not listed", the closest rejected listings with the rule they broke ("Redmi Note 17 Pro → different model (missing 14, extra 17)"). The website stays simple; this is what let me find almost every bug in this project in seconds.

Security and hygiene

  • The backend is not exposed outside Docker; the browser only reaches the Next.js server.
  • Both containers run as non-root users; the backend has a health check the frontend waits on.
  • Input is validated: only Amazon hosts are accepted, and only a product ID is ever used to build a request.
  • No secrets exist in the system at all, because it uses no keys.

Run it: docker compose up --build, then open http://localhost:3005.

8  Evaluation, limits and next steps

Measured on saved snapshots, judged on unseen links

Store results change by the minute, so live runs can't compare two matchers fairly. Instead, everything each store returned for 190 Amazon links is saved (backend/eval/pools/) and replayed through the real service, so both matchers see identical input. 12,396 listing pairs are hand-labelled same / different / unsure (eval/labels.jsonl). Links are split: a tuning set used for fixes and training, a fresh test set labelled blind and never tuned on, and the reviewer's 20 links. A store check counts as right if the app picks a labelled match, or says "not listed" when none exists.

The reviewer's 20 links, run live

Of the 40 store results, 30 are correct and 2 debatable: a Sony 55" whose store model code differs from the reviewer's by a regional letter, and a Galaxy A55 where the app picks the right phone but a sold-out listing of it. Of the 8 misses, 5 are sold-out listings the stores hide from search (Revolution 8 and teamLIGA on both stores, the Levi's 025 on Flipkart): their pages exist, but no query finds them. One more (TIRO 23 on Flipkart) is in stock and was found in the saved snapshot, but Flipkart's search stopped returning it on the day of the run. Only 2 are matcher misses: plain Puma and Levi's tees on Myntra with too little evidence to accept.

Known limits

  • Scrapers depend on page structure; a redesign means updating one adapter file.
  • Plain garments without a style code can't be told apart reliably, and 35 more labelled clothing links didn't change that: the listings themselves carry no distinguishing evidence. Rather than guess, they are reported as not listed.
  • Stock is checked without a pincode: "the store is selling it", not "it can reach you".
  • Both stores hide out-of-stock products from search, so a sold-out product comes back "not listed" rather than "out of stock". Neither store indexes Amazon's style codes, so searching by code doesn't help.

With more time

  • Photo comparison for plain clothes: a pilot showed gallery images carry some signal where text has none.
  • The replay evaluation in CI, failing a change that lowers fresh-test accuracy.
  • Adapter health monitoring: alert when a store's parse rate drops, before users notice.
  • A catalogue index from Myntra's sitemaps (about 8M products, 200 MB, allowed by robots.txt) so products search hides can still be found; Flipkart's partner feed in place of its search page, which its robots.txt disallows for crawlers.
  • Async client and Redis cache for concurrency and shared, persistent results.
  • Pincode-aware stock and price history.
