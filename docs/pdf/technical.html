How a link becomes an answer

A technical walkthrough of what happens between pasting an Amazon product link and seeing whether Flipkart, Croma or Myntra sell the exact same thing.

POST /api/compare  { "url": "https://www.amazon.in/dp/B0GVYGLNH7" }
Founding Backend Engineer assignmentNovember 2026
Overview

One link in, a verdict per store out

You paste an Amazon.in product link. About four to fifteen seconds later you see, for each relevant store, one of three answers: the same product is in stock, it is out of stock, or it is not listed. A fourth state, couldn't check, exists so that a blocked or failed request is never reported as "not listed".

1  Architecture

Two services, four stores

The system is deliberately small: a Next.js frontend that renders the page and proxies API calls, and a FastAPI backend that does all of the work. Both ship as containers and start with docker compose up --build.

Code map

2  The request, step by step

Tracing one real lookup

Everything below is from an actual run. The link is a OnePlus Nord CE6 Lite, 8 GB RAM, 128 GB storage, in Vivid Mint. The full round trip took 3.9 seconds.

1

The browser sends the link

The page posts {"url": "...", "refresh": false} to /api/compare on its own origin. Next.js rewrites that path to the backend, so the browser never needs to know where the backend lives and there are no cross-origin requests in production.

2

The backend finds the product ID

Amazon links come in many shapes: /dp/, /gp/product/, /gp/aw/d/ from the mobile app, long tracking URLs, and amzn.in short links. A regex extracts the 10-character ASIN; short links are followed to their redirect target first. The ASIN is the cache key: a repeat lookup within 15 minutes returns instantly unless the user presses "Check again".

3

The Amazon page becomes facts

The canonical page amazon.in/dp/ASIN is fetched and turned into a structured listing (section 3 explains how):

{ "brand": "OnePlus",  "category": "smartphone",  "colour": "Vivid Mint",
  "ram_gb": 8,  "storage_gb": 128,  "price": 30999,  "available": true,
  "title": "OnePlus Nord CE6 Lite | 8GB+128GB | Vivid Mint | Segment's Fastest Dimensity…" }
4

Each store is searched at the same time

The category decides the stores (Flipkart and Croma for a phone). Each gets a list of queries, tried in order until one produces a match: OnePlus nord ce6 lite 8GB RAM 128GB, then … Vivid Mint 128GB, then OnePlus nord ce6 lite.

5

Every result goes through the gates

Flipkart returned 24 listings and Croma 6. Each one is checked against the Amazon facts; anything that fails a single gate is dropped with a reason (figure 4 shows Croma's six).

6

A winner is picked and its stock confirmed

Among listings that passed, the same colour wins. Stock is read from the store's own signal, opening the product page when the search result doesn't say.

7

The answer is rendered

{ "platform": "croma", "status": "in_stock", "price": 30999, "confidence": 1.0,
  "title": "OnePlus Nord CE6 Lite 5G (8GB RAM, 128GB, Vivid Mint)",
  "query": "OnePlus nord ce6 lite 8GB RAM 128GB", "candidates_checked": 6,
  "reasons": ["brand OnePlus matches", "model ce6 lite matches", "storage 128GB matches",
              "RAM 8GB matches", "same colour (Vivid Mint)"] }

The page shows Amazon as the reference row and one row per store, with the price difference against Amazon (Flipkart: ₹28,099, ₹2,900 less). The reasons array powers the "Why" panel on each row.

3  Reading the Amazon page

From a marketing title to comparable facts

Amazon titles are written to sell, not to be parsed: "OnePlus Nord CE6 Lite | 8GB+128GB | Vivid Mint | Segment's Fastest Dimensity 7400 Apex Processor | 7000mAh Battery…". So the backend prefers structured data. Amazon's spec tables come in at least four layouts (product overview, tech specs, detail bullets, fashion "product facts"); all are merged into one key-value map with keys like brand, model name, colour and item model number. The title fills any gaps.

Category detection, in order

  1. Breadcrumbs mention smartphones, televisions, t-shirts/polos/jerseys, or shoes/sneakers.
  2. Spec-table evidence: a phone operating system (iOS, Android, One UI…) plus storage or SIM details. This rescued a real page titled just "iPhone Duo (512 GB) - Night Sky" with no breadcrumbs.
  3. Title words: "smartphone", "mobile phone", "iPhone", "TV" with a size, "polo", "jersey", "sneakers"…

Accessory words ("case", "cover", "compatible with"…) only guard the title check: a replacement iPhone screen is rejected, but a phone whose title boasts "45W Fast Charger" still counts. Other categories get a clear 422.

Why not just compare titles? "Galaxy S24" and "Galaxy S24 Ultra" share 90% of their characters, and "8GB RAM" vs "6GB RAM" differ by one digit. String similarity calls these near-identical; comparing extracted facts does not.

4  Searching the stores

One adapter per store, one interface

Each store is reached the way its own website gets its data, with a real Chrome TLS fingerprint (curl_cffi) so requests look like a normal browser visit. Every adapter turns results into the same Listing shape, so the matcher never knows which store it is looking at.

Query building, by category

TVfull model code → brand + series code + size → brand + series words + sizeStores index codes inconsistently; the series form catches Croma's naming.
Sneakersbrand + model + colour + gender → brand + modelShoes are sold per colourway.

Failure handling

Retries with a fresh session. HTTP 401/403/429/5xx and network errors trigger one retry (two for Amazon) with a reset cookie session and back-off.

Errors are not absences. If every query to a store fails, it reports Couldn't check, never Not listed.

Isolation. Each store runs in its own guarded thread; an exception in one becomes an error row and the others still answer.

Captchas. If Amazon serves one, the session is reset and retried once, then the user is told plainly to try again shortly.

5  The matching engine

Three gates, then a score

A listing counts as the same product only if it passes every gate. Scores are computed only for listings that already passed, and only to rank them. "Almost the same" never becomes a match.

Gate 1: brand

Normalised brands must be equal, or one must start with the other (samsung / samsungindia), using the alias table. If a store omits the brand, the first word of its title is tried.

Gate 2: model, with a different rule per category

Smartphones

Marketing words are stripped ("5G", "AI Smartphone", spec figures). The remaining distinguishing tokens (anything with a digit, or a variant word such as Pro, Ultra, Plus, Lite, FE, Fold) must be identical sets, and every series word must be present too (POP X ≠ POVA X). Names with neither (iPhone Duo) must match word for word. Amazon's "Model Name" field is preferred to the title.

Galaxy S24 vs Galaxy S22 → missing [s24], extra [s22]

Televisions

The manufacturer model code decides. An exact code match scores 1.0. A series-level match (Croma's "NU870B" inside Amazon's "43NU870BPLA") is accepted at 0.75 and labelled as such. If neither side shows a code, the series words must be ≥60% similar.

43NU870BPLA vs NU870B → series match

Sneakers

A matching style code (e.g. DD8959-100) is an instant match. Otherwise the model words must match exactly, both ways once generic words ("running shoes", "for men") are removed, and version words (Mid, Low, Comfort, Waterproof, Slip-Ins) are checked across the whole title. Aliases fix spelling: Lo → Low, NN → Next Nature.

Court Vision Low Suede vs Low Next Nature → different

T-shirts, polos, jerseys

First, the style code: Amazon's style number equal to the store's style code is a confirmed match. Otherwise garment facts are read from all three spec tables: pattern, fit, sleeve, neck, material. Any fact that differs rejects, and named product lines must agree (Essential ≠ Pique Tipping). At least two strong facts must agree; "it's a cotton t-shirt" counts for nothing. Jerseys need shared team or event words.

Full-sleeve polo vs half-sleeve polo → sleeve differs

Gate 3: the category's key attribute

  • Phones: storage must be equal. RAM must be equal whenever both sides state it; Apple never publishes RAM, so model plus storage decide there.
  • TVs: screen size within ±1 inch, which absorbs 138 cm vs 139.7 cm rounding.
  • Sneakers and apparel: the primary base colour must match, either exactly or within a family; the wearer must be compatible.

Scoring

For listings that pass, score = 0.5 + 0.5 × similarity, where similarity comes from the model check (1.0 for an exact code or identical tokens). An exact colour adds 0.1 over a family colour for fashion. Apparel has three honest tiers: a style-code match scores 1.0; a facts match is capped at 0.8 and shown as "Likely match"; and a match on default facts only (solid, short sleeve, round neck, which describes most plain tees) scores about 0.7 and is shown as "Possible match, check the details before buying".

6  Choosing the winner and the stock verdict

Same colour first, then the store's own word on stock

Phones are listed once per colour (and sometimes once per seller), so several listings often pass every gate. The assignment only requires RAM and storage to match, but a different colour is not what the user asked for, so the winner is chosen by an ordered key:

# service.py (simplified)
def rank(match):
    score, listing, _ = match
    tier = colour_tier(source, listing)   # 2 exact name · 1 same base colour · 0 other
    return (tier, round(score, 2), listing.available is not False, listing.available is True)

best = max(matches, key=rank)

If the exact colour is sold out

The result is Out of stock, because that is the true answer for that product, with a note: "This colour is sold out, but the same model is available in Marble Gray, Onyx Black." Before concluding that, up to three equally ranked listings are opened, since a store can list the same variant twice.

If the colour isn't listed at all

The closest variant is shown with its score reduced by 10% and a visible warning: "Same model, RAM and storage, but in Hyper Black: the Vivid Mint version isn't listed here."

The four outcomes

Explainability is a feature, not a debug log. Every row's "Why" panel lists the query used and each check that passed, or, for "not listed", the closest rejected listings with the gate they failed ("Redmi Note 17 Pro → different model (missing 14, extra 17)"). It lets a user trust a verdict, and it let me find almost every bug in this project in seconds.

7  Engineering decisions

What was chosen, and what was traded away

DecisionWhyCost
Rules, not a language modelDeterministic, free, fast and fully explainable. Product identity is mostly about exact tokens (S24 vs S24 Ultra), which rules handle better than fuzzy similarity.Hand-written rules need maintenance; apparel without model names is inherently fuzzy.
Hard gates before scoringA wrong match ("buy this", but it is the 6 GB model) is worse than a miss. Precision over recall.Some true matches with messy listings are reported as not listed.
Facts before textComparing normalised RAM, size, colour and codes is robust to every store's writing style.Each new attribute needs a parser and tests.
Parallel stores, sequential queriesTotal time ≈ slowest store. Queries stop at the first that yields a match, keeping request volume low.A threaded design; an async client would scale further.
Product pages only when neededFlipkart cards lack colour and TV codes; opening at most 8 pre-filtered pages per query bounds cost.A true match ranked beyond the shortlist can be missed.
"Couldn't check" as its own stateSilent failure reported as "not listed" would be a confident wrong answer.One more state for users to learn.
In-memory 15-minute cacheInstant repeats, kind to the stores, zero infrastructure.Lost on restart and not shared across instances.
Browser-like requestsThe stores serve the same public pages a shopper sees.Depends on page structure; cloud IPs are blocked more often than home connections.

Security and hygiene

  • The backend is not exposed outside Docker; the browser only reaches the Next.js server.
  • Both containers run as non-root users; the backend has a health check the frontend waits on.
  • Input is validated: only Amazon hosts are accepted, and only a product ID is ever used to build a request.
  • No secrets exist in the system at all, because it uses no keys.

Run it: docker compose up --build, then open http://localhost:3005. Source, README and the plain-language explainer are in the repository.

8  Evaluation, limits and next steps

Tested on real links

A fixed set of 40 real Amazon links (backend/scripts/test_links.txt) is run end to end after every change, 80 store checks in all. It includes deliberately awkward cases: a page without breadcrumbs, a phone title that mentions a charger, adidas colour codes, a women's tee with a one-word title, a licensed jersey and an unbranded knock-off. Every result was reviewed by hand; stock states change daily.

Known limits

  • Scrapers depend on page structure; a redesign means updating one adapter file.
  • Plain garments without a style code can't be told apart reliably; those matches are shown as "possible", never as confirmed.
  • Stock is checked without a pincode: "the store is selling it", not "it can reach you".
  • Recall is bounded by each store's own search: what it doesn't surface, we can't see.

With more time

  • Labelled evaluation set with precision and recall per category, run in CI.
  • Adapter health monitoring: alert when a store's parse rate drops, before users notice.
  • Async client and Redis cache for concurrency and shared, persistent results.
  • A model as a tie-breaker only for low-confidence apparel, behind the same hard gates.
  • Pincode-aware stock and price history.
